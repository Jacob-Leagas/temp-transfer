# Documentation Tone Guide

version: 1.0

## Purpose

This guide defines the tone and writing style used in my documentation, comments, READMEs, and project notes. It ensures consistency across all projects and keeps the writing aligned with my engineering habits.

## Core Tone Principles

- Write with clarity.
- Keep sentences short and direct.
- Focus on what matters for implementation.
- Avoid filler language.
- Avoid dramatic or emotional phrasing.
- Maintain a steady, neutral voice.

## Voice

My voice is:

- Plain, intentional, and readable.
- Technical without being academic.
- Confident without being verbose.
- Direct without being blunt.
- Helpful without over explaining.

## Structure

- Use clean Markdown.
- Keep sections short and purposeful.
- Use headings to separate concepts.
- Use lists when describing steps or rules.
- Avoid long paragraphs.
- Avoid decorative formatting.

## Language Rules

- Use plain language over jargon.
- Avoid metaphors and analogies.
- Avoid arrows in text or comments.
- Avoid em dashes. Use commas, colons, or periods instead.
- Avoid emojis unless explicitly requested.
- Avoid conversational filler like just, basically, kind of, in case you were wondering.

## Precision

- State facts, not assumptions.
- If something is uncertain, say so directly.
- Do not invent details or context.
- Do not speculate about behavior or architecture.
- Keep documentation grounded in the actual code.

## Scope Control

- Document only what is relevant.
- Avoid explaining obvious concepts.
- Avoid rewriting entire sections unless necessary.
- Keep updates minimal and focused.
- Do not add future facing notes unless required.

## Comments in Code

- Keep comments short and functional.
- Explain intent, not mechanics.
- Avoid repeating what the code already shows.
- Use comments to clarify decisions, constraints, or assumptions.
- Keep comment tone consistent with documentation tone.
